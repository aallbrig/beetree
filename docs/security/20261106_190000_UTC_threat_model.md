# BeeTreeCraft threat model

This is the public, high-level map of what BeeTreeCraft protects, who might attack it, where trust changes hands, and which control in the repository answers each threat. It carries no secrets, account identifiers or exploit detail. To report a problem, follow [SECURITY.md](../../SECURITY.md).

Every path in backticks below must exist in the repository; `scripts/check_threat_model.sh` (part of `task docs:check`) fails when one goes missing, so this page cannot drift from the code.

## Assets

| Asset | Why it matters |
|-------|----------------|
| Private trees, scenes and drafts | Authors' unpublished work; visible only to the owner |
| Account data: email, birthdate, consent record | Personal data; never shown on public profiles |
| API keys | Grant the same powers as the account, within their scopes |
| Public content: trees, forum, profiles | Must stay honest and free of abuse; integrity of authorship and remix credit |
| The site and its release artifacts | Visitors run what we ship; a tampered CLI archive or page harms them |
| The AWS account and its bill | Compromise or cost abuse affects availability for everyone |
| The repository and release pipeline | Whoever controls main controls what is deployed |

## Actors

- **Anonymous visitor.** Reads public content; can call public read routes.
- **Signed-in user.** Owns their own trees, scenes, keys and forum posts.
- **Other signed-in user.** The adversary for data isolation: tries to read or change someone else's items.
- **Moderator.** Can remove forum content; a narrow elevated role.
- **Automation holding an API key.** Limited by scopes.
- **Third party on GitHub.** Can open issues, comments and fork PRs on this public repository.
- **The overnight loop.** An AI agent with broad repository permissions that reads issue text.
- **Malicious or careless dependency.** Go and npm packages pulled in at build time.

## Trust boundaries

1. **Browser to CloudFront.** Everything from the browser is untrusted input. The site is static and served over HTTPS with a strict Content-Security-Policy.
2. **Browser or client to the API.** Requests are authenticated with a Cognito token or an API key, size-limited and rate-limited before any handler runs.
3. **API Lambda to DynamoDB.** The Lambda's role allows only the operations it needs on its own table.
4. **API to Cognito.** The API trusts only tokens whose signature, issuer and expiry verify against the pool's published keys.
5. **CI to AWS.** GitHub Actions assumes a deploy role through OIDC; no long-lived cloud credentials are stored in the repository.
6. **Repository to production.** Merging to main and cutting a release deploys; both pass the quality gates first.
7. **Issue text to the loop.** Text written by anyone other than the owner is data, never instructions.

## Top threats and controls

| # | Threat | Control |
|---|--------|---------|
| 1 | A user reads or edits another user's private tree, scene or key | Owner checks in every handler, proven for every route and caller type by `cli/internal/api/authz_matrix_test.go` |
| 2 | A leaked key does more than intended | Scopes that chain read, write, delete, enforced in `cli/internal/api/scopes.go` and tested in `cli/internal/api/scopes_test.go` |
| 3 | A database leak reveals usable API keys | Only the SHA-256 hash is stored; the secret is shown once (`cli/internal/api/apikeys.go`); keys per user are capped |
| 4 | A forged or expired session token is accepted | Signature, issuer and expiry verification in `cli/internal/api/auth.go`, tested in `cli/internal/api/auth_test.go` |
| 5 | Email or consent data appears on a public page | Public profiles use a separate type without those fields (`cli/internal/api/types.go`); the profile tests in `cli/internal/api/profile_public_test.go` check the public shape |
| 6 | Oversized bodies or write floods exhaust the service or the bill | Body cap in `cli/internal/api/server.go`, per-user write limiter in `cli/internal/api/ratelimit.go`, and a global throttle on the HTTP API in `infra/template.yaml` |
| 7 | Script injection through user-authored text | Script execution limited to our own origin by the Content-Security-Policy in `infra/template.yaml`; user text is rendered as text |
| 8 | Clickjacking, downgrade, MIME sniffing | Frame denial, HSTS, content-type and referrer headers from the response headers policy in `infra/template.yaml` |
| 9 | The site bucket is read directly or altered | Bucket reachable only through CloudFront origin access control, defined in `infra/template.yaml` |
| 10 | Weak or abused sign-up | Password policy, verified email and the pre-sign-up hook, all in `infra/template.yaml` |
| 11 | A committed secret | `gitleaks` in `.pre-commit-config.yaml` and in `.github/workflows/ci.yml`, with project rules in `.gitleaks.toml` |
| 12 | Over-broad cloud permissions for deploys | Separate narrowly scoped roles bound to the repository's OIDC subject in `infra/iam.yaml` |
| 13 | Prompt injection through issues or comments steers the loop | The loop reads only issues by the owner (`scripts/agent-loop.sh`), the prompt treats all other text as data (`scripts/loop-prompt.md`), and `scripts/check_loop.sh` tests the loop script |
| 14 | Vulnerabilities are discussed publicly before a fix | Private reporting path in `SECURITY.md`; the audit working files stay in the gitignored `.agent-loop/` directory |
| 15 | A tampered release artifact | Releases ship `SHA256SUMS` built by `scripts/release.sh` |

## Known gaps

These are tracked as issues on the security map and are not yet controls: dependency and vulnerability scanning in CI, a repeatable audit skill, and audit passes over auth, infrastructure, the loop and data isolation. Per-instance rate limiting is best effort on a scaled-out Lambda; the API Gateway throttle is the global backstop.

## Reviewing this page

Treat any change to authentication, API routes, keys or the infrastructure template as security-relevant and re-read the table above. Add a row when a new control lands; the gate script keeps the named files honest.
